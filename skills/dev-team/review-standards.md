The Optimization Reviewer's whole standards surface — read this instead of the
two full files. Every finding cites the section + bullet name.

## Efficiency
- **No N+1 Queries**
- **O(1) Lookups**
- **Hoist Invariants**
- **Close Resources**
- **Lazy Where Appropriate** — don't load unbounded rows to show a few.

## Reliability
- **Fail Fast**
- **Handle Errors at Boundaries** — catch where you can act; no catch-and-swallow mid-stack.
- **Log with Context** — error logs carry the IDs/inputs/state needed to reproduce.
- **Idempotent Writes**
- **Don't Assume Success** — check return values and status codes.
- **Explicit Over Implicit** — typed exceptions/explicit error returns over silent/magic returns.

## Scalability
- **Stateless Services** — state lives in client or DB.
- **No Global Mutable State**
- **Paginate Unbounded Results**
- **Defer Expensive Work** — no slow external calls/large computation synchronously in a handler.
- **Connection Pooling** — no new DB connection per request.

## Safety & Security
- **Validate at Boundaries** — validate input at entry points (HTTP, CLI, external responses), never mid-stack.
- **Parameterized Queries Only** — no string-interpolated/f-string SQL, ever.
- **Auth Before Data** — authorization runs before any data access, never after.
- **Least Privilege**
- **No Secrets in Code** — creds/keys/tokens in env vars only.
- **Sanitize User Content** — escape/sanitize any user string rendered in UI (XSS).
- **Safe Defaults** — default to the more restrictive behavior; opt into permissive.

## Observability
- **Structured Logging** — machine-parseable (JSON) with timestamp, level, service, request_id, user_id, message.
- **Log at the Right Level**
- **Instrument Business Events** — log meaningful events (bet placed/accepted), not just errors.
- **Request IDs** — unique ID per request, logged on every line and returned in a header.
- **Health Endpoints** — every service exposes `/health` returning 200 when operational.
- **Alert on Symptoms, Not Causes** — alert on error rate/latency/availability, not CPU/memory alone.

## Fault Tolerance
- **Timeouts on All External Calls**
- **Retry with Backoff** — exponential backoff + jitter, not a tight loop.
- **Circuit Breakers on High-Traffic Paths**
- **Graceful Degradation** — degrade on a non-critical dependency outage rather than fail wholesale.
- **Bulkheads** — isolate failure domains; a slow job doesn't exhaust the HTTP thread pool.
- **Idempotency Under Retry** — no double-accepted bet.

## Known Failure Patterns (from dev-team runs)

Specific code-level bug classes caught in past reviews — moved here verbatim
from `~/os/knowledge/memory/dev-team-learnings.md` (2026-08-03 compaction) so
the Reviewer checks for these exact recurring defects, not just the general
rules above.

- Shared mutable state gets poisoned by two look-alike patterns: `{ ...EMPTY_CONST, ...parsed }` shallow-spreads references to a constant's nested objects, so a caller mutating `result.nested[id][field] = true` poisons the constant for every later call in the process; and TS `Readonly<>`/`as const` is compile-time only, so a module-level constant typed that way is still runtime-mutable by any importer. **Why:** both are "looks frozen, isn't" — state bleed that's hard to reproduce because it depends on call order within a process. **How to apply:** construct shared defaults with explicit per-field spreads (`{ field: {...(parsed.field ?? {})}, ... }`), never a top-level shallow spread of the constant; and for any exported constant read by others (pricing, default options, enum-like maps), `Object.freeze` the top object AND each nested object, then add a test asserting a mutation attempt doesn't stick.

- Expensive I/O (shell/git calls, disk reads) must never run inside a write mutex — the lock serializes every concurrent caller for the slowest call's duration, and a subprocess can take seconds. **How to apply:** resolve all external data before `runExclusive`; the lock should protect only the read-modify-write step on the shared file.

- `focus-visible:ring-*` on filled colored buttons must use a white ring with offset, not a lighter tint of the button color — a tint ring on its own fill routinely lands under the WCAG 3:1 non-text-UI contrast minimum. **How to apply:** `focus-visible:ring-white focus-visible:ring-offset-2 focus-visible:ring-offset-[button-color]` on any filled-color button.

- Keyword-matching functions (autoTag, search, filter) must use word-boundary checks, not bare `indexOf` — substring matches false-positive ("os" inside "gross", "ml" inside "email"). **How to apply:** gate matches on `\W`/string-edge on both sides; never ship a keyword scanner built on raw `indexOf`.

- When two code paths in the same render need overlapping derived data (a computed view AND its raw source), thread the already-fetched source through an optional param instead of letting the second path re-fetch it — a page calling both a merge helper and the raw read directly doubles the disk/DB I/O per render for no reason. **How to apply:** `const raw = await readSource(); const merged = await mergeView(raw);` — one read, shared.

- For in-place migration edits (no data exists yet), keep every DDL change idempotent (`DO $$`/`IF NOT EXISTS`/`DROP ... IF EXISTS`) and wire Critical-invariant regressions (FK on-delete behavior, status-gating triggers) into the existing local-DB test harness rather than a new file — a schema fix that isn't re-apply-safe breaks push/test idempotency on an already-applied DB, and a Critical caught by review (cascade-delete history loss, a declined record becoming live) silently regresses later without an executable guard. **How to apply:** when a data-path review returns Critical schema findings, edit migrations in place with guarded blocks, add a harness assertion that the bad operation RAISES and the good one succeeds, re-run the harness as the re-gate. Prefer FORCE (not ENABLE) RLS and integer-cents money.

- A DB helper that reads a JWT/session claim and casts it (e.g. `nullif(claim,'')::uuid`) must gate the cast so a malformed value resolves to NULL, never throws — a raw cast on a garbled/tampered claim breaks every query for that user (self-inflicted DoS) instead of failing safe to zero-rows. Absent/blank claims usually already fail safe; malformed ones are the gap. **How to apply:** regex-gate the value before casting, keeping the function pure/STABLE; add a fixture with a `"not-a-uuid"` claim and assert zero rows + no throw.

- Supabase RLS is testable on a vanilla local Postgres by emulating the auth layer — policies reference `auth.uid()`/`auth.jwt()` and roles that don't exist in stock PG, so teams wrongly assume RLS needs a live Supabase. **How to apply:** in the test cluster, create `schema auth` with `auth.jwt()`/`auth.uid()` backed by `current_setting('request.jwt.claims')`, create the three roles, impersonate per-case via `set_config` + `set local role`. `security_invoker` views are PG15+ only — gate those cases on server version; base-table RLS + column GRANTs are the version-independent, fully-testable guarantee.

- Route-middleware gating gives false authz confidence in Next.js — server actions are POSTable from any path, bypassing the matcher. Only review caught 6 unauthenticated mutating actions behind a "protected" matcher; QA's happy-path smoke missed it. **How to apply:** verify each mutating server action checks authz itself (a shared fail-closed helper as its first statement); never accept middleware as the guard.

- JS money-path guards must use `Number.isSafeInteger`, never bare `Number.isInteger` — `Number.isInteger(2**53)` is true, so an "integer cents" assert built on it silently admits precision-lost values, and the gap threads through sums AND `total * pct` products (which overflow 2^53 before the `/100`). A reviewer's own prescribed fix can be wrong here too: `isSafeInteger(product)` fails on a legitimately fractional product — the correct guard is a magnitude check. **How to apply:** on any money-path item, check every cents assert uses `isSafeInteger`, guard post-reduce sums and pre-division products, and require one probe that actually crosses 2^53.

- A clean `tsc` + build does NOT prove client-side hooks exist at runtime — a React-19-only hook shipped on a React-18 repo passed types/build and 500'd in production; only QA's live smoke caught it, since bundlers resolve APIs the installed runtime lacks and unit tests rarely execute client hook wiring. **How to apply:** builders copy an existing working component's hook pattern from the same repo rather than writing a new one from training data; QA's live smoke must hit every new route even when the suite is green.

- A Next.js page displaying admin-toggled DB content (banners, flags, announcements) silently never updates if statically prerendered — build/typecheck/unit tests all pass while the page is baked at build time with the toggle off, since App Router defaults to static and the DB query runs once at build. **How to apply:** set the rendering mode explicitly (`force-dynamic`, `revalidate`, or revalidatePath-on-mutate) whenever an item wires DB-driven content into a previously-static page, and assert the toggle round-trip against a built (not dev) server.

- Any dedupe/identity key built from an email address must canonicalize (`lower(trim())`) in both the app-side key builder and the SQL grouping via one shared helper — a mixed-case variant otherwise splits one identity into two, defeating a PK-based dedup ledger (only Opus review caught it, not QA). Separately, "remind N days after event" schedulers should derive eligibility from the DB at fire time rather than cancel/reschedule queued jobs — some queue libraries (e.g. pg-boss `singletonKey`) reject a duplicate enqueue instead of retiming it, silently breaking a "newer event pushes the reminder out" invariant. **How to apply:** review every key builder and SQL GROUP/DISTINCT site for canonicalization drift; verify a queue library's singleton semantics from its docs before betting a correctness invariant on them.

- A form control that constrains choices client-side (dropdown/calendar of "valid" options) is often the ONLY enforcement — the server action validates format, not membership, so a crafted POST can submit any excluded value. The right fix is re-running the same server-side rule engine that fed the control, not a bounds-only patch. **How to apply:** on any item building/swapping a choice-constrained input, verify the server re-validates membership via the same data source, and add a crafted-POST probe through the real action entry point.

- In the Next.js App Router, a client component fed a URL-derived prop (`?date=`, `?tab=`) keeps its existing DOM across soft navigations — a bare `defaultValue={prop}` is stale after every `<Link>` click, since React reuses the DOM node and no build/typecheck/markup test observes client reconciliation. Separately, `useRouter()` throws inside `renderToStaticMarkup` tests (no AppRouterContext). **How to apply:** use `key={prop}` (remount) or a fully controlled `value={prop}`; prefer `window.location.href` over `useRouter` in components reachable by static render tests; test the guard by calling the component as a plain function and invoking its handler with a stubbed `globalThis.window` rather than relying on jsdom.

- Claims about geometry (click targets, stacking order) need forced runtime proof, not static/keyboard checks — both directions. QA reporting a WORKAROUND it needed ("had to focus + Enter, the click target was tiny") is itself a finding: a gate can PASS via keyboard while the primary mouse gesture is nearly unusable, because a covering sibling's whole BOX — not just its visible children — swallows the click via z-order. And a "must sit above/below X" stacking claim is vacuous whenever the two elements never overlap in normal flow. **How to apply:** positive proof is a `document.elementFromPoint()` sweep of ~11 points per target (corners, edges, center, a padding gap) each resolving to the intended control; negative/stacking proof is forcing an overlap at runtime (`marginBottom: '-140px'`), hit-testing inside it, then restoring and re-asserting the original rect. Distinguish an environment artifact (zero capture-phase events + hidden `visibilityState`) from a real overlay bug (event lands on the wrong node) before FAILing on either. Fix an overlay-under-a-sibling with `pointer-events:none` on the covering container, not a z-index change.

- A native `<dialog>`'s `open` state lives in the DOM, not React state, so it SURVIVES an App Router soft navigation — a link inside a modal must close it explicitly or the destination renders behind the still-open `::backdrop`, since React reuses the same DOM node and the usual `event.target === dialogRef.current` check never matches an inner anchor. **How to apply:** delegate one `onClick` on the dialog's inner wrapper (`if (e.target.closest("a")) dialog.close()`) — a `next/link` passed through a `children` slot can't carry a callback across the server/client boundary, so delegation is the only option. Native `<dialog>` + `showModal()` remains the right default.

- When a rule decides both what gets LISTED and what is REACHABLE, one shared guard must own both — a filter applied only in the lister leaves the direct-access path wide open, and if the fix for that then makes the guard case-insensitive while the walker stays case-sensitive, the same class of bug reappears in the opposite direction. This has recurred four times in one repo, twice via the fix for a prior occurrence. It also recurs when an EXISTING shared guard gets rooted at a wider directory than every prior caller — a tree walk skipping dot-entries was safe while every caller rooted below `knowledge/`, but became a live leak (1001 reachable hidden files) the moment a new caller rooted at the repo root. Both times, QA verified the listing was correct (it was) and only review caught the direct-access path. **How to apply:** for any visibility/exclusion/permission rule, review both the enumeration path and the direct-access path for ONE shared predicate with identical matching semantics; test that they agree on a case-variant and a near-miss name; when reusing a shared guard at a new, wider root, treat it as a scope change requiring a fresh audit, not a no-op reuse, and apply the predicate to the path *below* the root, never the root's own absolute path.

- A library's internal memoization can cache a FAILED parse as a success, so an error path fires only on the first call in a process and silently never again — test error paths TWICE IN ONE PROCESS, not once, for any parser/loader with a content-keyed cache. **How to apply:** when a criterion is "malformed input produces a warning," assert it on two consecutive calls in the same process and two consecutive requests to the same running server; a fresh-process-per-assertion suite is structurally blind to this class.

- A test that hand-maintains a mirror of source data (an allowlist of tokens, a hardcoded "total: N") is a sync point that WILL drift and cost a fix cycle — derive it from the source at runtime instead. Comparing rendered HTML against source strings also requires HTML-entity decoding first (decode `&amp;` LAST so double-encoded literals round-trip), since JSX escapes rendered text. **How to apply:** in review, flag any test literal that restates something the source already knows and prescribe a runtime walk/count; prove the derivation self-maintains by injecting a new instance and confirming the test passes with zero test edits.

- An `execFile` arg array stops SHELL injection but not FLAG injection — a user-controlled value appended after a CLI flag with an OPTIONAL argument (`-r, --resume [value]`, square brackets) gets re-parsed as its own flag, so a crafted value can silently disable a whole safety flag. The regex guarding this must live where argv is actually built, not just at the outer HTTP boundary, or any other caller of the same lib bypasses it. **How to apply:** check `--help` for `[...]`-style flags on any CLI wrapping user input, validate at the argv-construction site (export one regex, have every caller import it), and mutation-test the guard both directions (on → blocked, emptied → genuinely succeeds). Related: a permission deny-rule can leave the tool's own denial telemetry empty while its prose still claims "blocked" — only disk state proves a guard actually fired; and for any feature granting write access to a config tree, enumerate the real auto-load surfaces (`ls -la ~/.claude | grep '^l'`) rather than reasoning about which paths matter from memory.

- On macOS (case-insensitive APFS), a Next.js dynamic route serves 200 for a case-variant slug and then corrupts the real prerendered `.html` — a filesystem artifact, not a code defect, that reads to QA as a genuine bug. Next's incremental cache reads the prerendered file before the router's `fallback:false` check, so a case-insensitive volume resolves a wrong-case URL to the real file (200), and the on-demand render then overwrites it with an error shell. The tempting fix — case-insensitive slug lookup — is actively harmful: it turns the wrong-case URL into a permanent live duplicate, the same lister/guard-drift family above. **How to apply:** before dispatching a fixer, adjudicate it yourself — request a mixed-case slug with NO colliding prerendered file; if that 404s while only the colliding one 200s, it's the filesystem, not the code. State the adjudication as ground truth in the fixer's and re-gating QA's prompts explicitly, or QA will re-FAIL a correct fix. `export const dynamicParams = false` is still correct on its own merits when a route's param set is fully known at compile time.

- A "this file can never run against production" criterion is satisfied by CONVENTION until the file guards itself — keeping a fixture out of an auto-applied directory only constrains the tools that glob that directory, and says nothing about a direct `psql <prod-url> -f fixture.sql`. A reviewer's own prescribed guard can also be the hole: `\if :{?var}` tests whether a variable is DEFINED, not its value, so `-v var=0` still applies the fixture — this survived one full review+fix cycle. **How to apply:** for any "can never reach production" criterion, require the guard to live in the artifact itself, and prove BOTH directions per invocation shape (`-f`, `< file`, piped) with a **row count of zero** asserted on refusal — not just absence of output. Test guard variables by value, and mutation-test the falsy value (`=0`, `=false`, garbage) explicitly. Budget a second fresh review on containment-critical work generally — a first fix pass can close real findings while introducing this exact one.

- A handed-down environment fact asserting that a local app is SAFELY disconnected from production must be re-verified by the orchestrator from the env file and a reachability probe, never inherited — and the specific trap is an adapter seam that selects production by the mere PRESENCE of a var. **Why:** an item whose whole risk line was "a screenshot capturing a real customer name ships to the public site" arrived with explicit ground truth that the client app's `.env.local` left `NEXT_PUBLIC_SUPABASE_*` blank so there was "no configured path to any production database". The file actually held the live project URL, anon key, **service-role key**, and a production pooler `DATABASE_URL`, and `lib/db/index.ts` checked `NEXT_PUBLIC_SUPABASE_URL` FIRST — so the dev server was serving the client's real customers, and the demo fixture that had just been seeded into the local DB was not being read at all. Two decoys made this look fine: pg-boss logged a connection timeout (the pooler's :6543 is egress-blocked here) and the app printed "email worker disabled: no DB", which reads as "no database configured" — but Supabase REST over :443 was reachable (401 = up), which is the path the adapter actually uses. Cost to catch: one `grep` of the env file plus one `curl`. **How to apply:** whenever an item's risk line is "real data must not reach X", the orchestrator personally reads the actual env/config file and traces the selection function before any agent runs, rather than accepting a prose summary of it — and treats a partial connection failure as evidence about ONE transport, never as proof the app is disconnected. To force a local-only run in Next.js, export the production vars as EMPTY STRINGS (`NEXT_PUBLIC_X=""`), never `unset`/`env -u`: Next repopulates absent keys from `.env.local`, so only present-but-empty wins, and config readers that `.trim()` then treat empty as undefined will fall through to the local adapter. Never edit the user's real `.env.local` to achieve this. Then verify from the OUTPUT (names rendered on the page cross-checked against the local fixture's rows), not from the config you just set.

- An element's occupied height includes its borders, so a clearance token derived from an inner content height is short by the border width when the wrapper also has a border — this overlaps by exactly one pixel and passes most eyeballed screenshots. **How to apply:** when computing a clearance/gap token from a measured element height, measure the border-box (`getBoundingClientRect()`/`offsetHeight`), not content height, or add the border width explicitly.

- A criterion of the form "a missing asset must FAIL THE BUILD" is almost never satisfied by the default implementation, because bundlers validate **string** asset paths at no point in the build — only a *static import* creates a checked edge. **Why:** `<Image src="/case-studies/x.png">` in Next.js typechecks, builds, and prerenders happily whether or not the file exists, then 404s into a broken image at runtime — exactly what such a criterion exists to forbid; the same holds for any string path handed to `next/image`, an `<img>`, a CSS `url()`, or a `fetch` of a public asset. Switching to `import img from "@/public/…png"` makes a deleted file an unresolvable module (hard build error) *and* supplies intrinsic width/height so no dimensions get hardcoded — one change buying two criteria. The forcing constraint on where that map can live is worth checking early: here the registry module could not hold the imports because the test suite loads it directly under `node --experimental-strip-types`, which cannot import a `.png`, so a separate module was mandatory rather than stylistic. **How to apply:** when an item says a bad reference must fail the build, the orchestrator should establish *whether the framework validates that reference at all* before any builder runs, and prescribe the static-import (or equivalent compile-time) seam in the spawn prompt; then require QA to mutation-prove **both shapes** — asset deleted (module resolution error) and reference pointed at an unregistered path (prerender throw) — each with a non-zero exit, restored via `cp` + `shasum -c`. Reasoning about this criterion always passes it; only the mutation catches it. Corollary: a build-time throw on a missing lookup is **one-directional** — it catches registry→map drift but an *orphan* map entry with no referent builds perfectly clean, so pair it with a runtime-derived set-equality test (read the map as source TEXT when the test runtime cannot import its binary deps) and mutation-test both directions.
